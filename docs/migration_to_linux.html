Миграция tg_parser на Linux-сервер

План перевода tg_parser с Windows + PyQt6 на headless Linux + web-only управление. Цель — устойчивый 24/7 запуск через systemd с управлением жизнедеятельностью бота из браузера по LAN.

Перед началом миграции — сделать копию текущего проекта (git clone в новую папку или отдельный архив). Этот план применяется к копии; оригинальный C:\MyPyProjects\tg_parser остаётся как референс / fallback на Windows-окружение, пока миграция не завершена.

1. Контекст

Зачем мигрируем

  • Стабильность 24/7. Windows-машина с PyQt6 tray-app требует, чтобы пользователь был залогинен (или приложение запускалось от Local System, что ломает доступ к user-specific данным). Linux-сервер с systemd работает в фоне без сессии.
  • Цена. Сервер на cloud.ru обходится дешевле, чем держать включённым десктоп. На один сервер можно подсадить vwma_bot, tg_parser и reestr одновременно.
  • Удалённое управление по LAN. Web UI вместо tray-app, доступен с любого устройства в локальной сети.
  • Унификация со стеком vwma_bot. Оба бота на одном сервере, одинаковый паттерн (systemd, nginx, FastAPI, аналогичные exchange-adapters).

Что НЕ цель миграции

  • Не переписываем парсинг сигналов — он работает, не трогаем
  • Не меняем формат БД (SQLite остаётся, миграция данных = просто копирование db/*.db файлов на сервер)
  • Не добавляем новые источники сигналов или биржи
  • Не делаем CI/CD pipeline (на текущем этапе оверкилл)

3. Целевая архитектура на Linux

┌──────────────────────────────────────────────────────────────┐
│  Ubuntu Server 24.04 LTS (cloud.ru, LAN-only)                │
│                                                              │
│  systemd ────► tg-parser.service                             │
│                    │                                         │
│                    ├─ TradingBot (asyncio loop)              │
│                    │   ├─ Telethon client (Telegram WS)      │
│                    │   ├─ Parser (regex)                     │
│                    │   ├─ BybitExchange (pybit)              │
│                    │   └─ Notifier                           │
│                    │                                         │
│                    └─ FastAPI + uvicorn (web UI, LAN)        │
│                        ├─ /            dashboard             │
│                        ├─ /signals     история сигналов      │
│                        ├─ /trades      история сделок        │
│                        ├─ /settings/*  настройки             │
│                        ├─ /logs        live tail             │
│                        ├─ /api/*       REST + control        │
│                        └─ /ws/*        WebSocket             │
│                                                              │
│  Доступ — http://192.168.x.x:8001 с любого устройства LAN    │
└──────────────────────────────────────────────────────────────┘

Принципы

  • Единый процесс — бот и web UI в одном Python-процессе (как сейчас). Управление через флаги в БД, а не через signals/IPC.
  • systemd Restart=always — при любом падении бот рестартанёт автоматически.
  • Soft control приоритет — кнопки Pause/Resume через флаг в БД. Hard restart (через polkit + systemctl) — только аварийный.
  • LAN-only — bind на 0.0.0.0:8001 + firewall разрешает только LAN-подсеть, либо bind на конкретный LAN-интерфейс.
  • Логи в journald + файлы — журнал systemd для оперативного просмотра + RotatingFileHandler для долгосрочной истории.

Phase 1 — Linux compatibility (1 день)

Цель: бот стартует и работает на Linux в ручном режиме (без systemd пока). Web UI открывается, парсит сигналы, торгует на testnet.

Задачи

  1. Удалить Windows-specific файлы (см. раздел 2 — список под удаление)
  2. Убрать PyQt6 и pywin32 из requirements.txt
  3. Проверить config.py — нет ли hardcoded Windows-путей (C:\...)
  4. Проверить logger.py — пути к логам должны быть относительными или из переменных окружения
  5. Проверить все open(...) на относительные пути
  6. Проверить main.py — нет ли импортов app_gui или gui_manager, убрать если есть
  7. Создать .env.example с шаблоном переменных (без секретов)
  8. Перенести проект на сервер (rsync / git clone)
  9. На сервере: python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt
  10. Создать .env на сервере с реальными секретами, chmod 600 .env
  11. Скопировать db/*.db с Windows-машины (или создать пустые)
  12. Запустить вручную: python -m main
  13. Открыть в браузере http://<LAN-ip>:<port> — убедиться dashboard открывается
  14. Послать тестовый сигнал в Telegram-канал — убедиться парсится и записывается
  15. (Опционально) на testnet Bybit ключах — убедиться что сделка открывается

Acceptance criteria Phase 1

  • Бот стартует на Linux без ошибок импорта
  • Web UI доступен на LAN
  • Парсер обрабатывает сигналы
  • Сделки выполняются на testnet (если переключение testnet/mainnet есть)
  • Логи пишутся в logs/
  • СтопCtrl+C корректно завершает бот (нет zombie-процессов)

Phase 2 — systemd autostart (0.5 дня)

Цель: бот стартует автоматически при загрузке сервера, рестартует при падении, логи в journald.

Задачи

  1. Создать пользователя botuser (если ещё нет общего для ботов): sudo useradd -r -s /usr/sbin/nologin botuser
  2. Развернуть проект в /opt/tg_parser/, владелец botuser:botuser
  3. Создать venv от имени botuser, установить deps
  4. Создать /etc/systemd/system/tg-parser.service (см. шаблон ниже)
  5. sudo systemctl daemon-reload
  6. sudo systemctl enable --now tg-parser
  7. Проверить sudo systemctl status tg-parser — должен быть active (running)
  8. Проверить sudo journalctl -u tg-parser -f — должны идти логи
  9. Тест: sudo reboot, после загрузки убедиться что бот сам стартанул
  10. Тест: убить процесс через kill, убедиться что systemd рестартанул через 10 сек

Шаблон unit-файла

# /etc/systemd/system/tg-parser.service
[Unit]
Description=tg_parser — Telegram signals to Bybit executor
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=botuser
Group=botuser
WorkingDirectory=/opt/tg_parser
Environment="PATH=/opt/tg_parser/venv/bin"
EnvironmentFile=/opt/tg_parser/.env
ExecStart=/opt/tg_parser/venv/bin/python -m main
Restart=always
RestartSec=10

# Безопасность
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/tg_parser/db /opt/tg_parser/logs

# Логи в журнал systemd (плюс свои файловые в logs/)
StandardOutput=journal
StandardError=journal
SyslogIdentifier=tg-parser

[Install]
WantedBy=multi-user.target

Acceptance criteria Phase 2

  • Бот стартует автоматически при reboot
  • Бот рестартует при ручном kill через 10 секунд
  • Логи доступны через journalctl -u tg-parser
  • Web UI продолжает работать без вмешательства

Phase 3 — Dashboard tweaks (0.5 дня)

Цель: dashboard на главной странице показывает реальное состояние бота, а не только сигналы. У тебя уже есть web UI как dashboard для просмотра — этот этап его дополняет.

Что добавить на главную

  • Статусные карточки:
    • Bot status: ● Running / ● Paused / ● Error (если есть)
    • Telegram: ● Connected / ● Reconnecting / ● Offline
    • Bybit: ● Connected / ● Reconnecting / ● Offline
    • Uptime
    • Сигналов сегодня / за неделю
    • Открытых сделок / закрытых сегодня
    • PNL за сегодня (если считается)
  • Лента «Последние сигналы» (10–20 штук) — если ещё нет
  • Лента «Активные сделки» — если ещё нет
  • Status footer: последний event timestamp, version бота, hostname сервера

Технические задачи

  • Endpoint GET /api/status возвращает JSON со всеми статусами
  • Endpoint GET /api/stats?period=today|week для счётчиков
  • Auto-refresh dashboard каждые N секунд (через setInterval или WebSocket)
  • Connection status — Telethon и pybit имеют свойства/события, по которым можно понять состояние

Acceptance criteria Phase 3

  • Открыв главную, за 2 секунды видно: жив бот или нет, на чём оно подключено, сколько работы за сегодня
  • Если Telegram отвалился — на dashboard видно
  • Если Bybit отвалился — на dashboard видно

Phase 4 — Web UI controls: pause / resume (1–2 дня)

Цель: управление жизнедеятельностью бота из web UI без SSH. Реализация через флаги в БД (soft control), а не через сигналы процессу.

Архитектура

┌─────────────────────────────────────────┐
│ web UI: [PAUSE PARSING]                 │
│         [STOP TRADING]                  │
│         [FORCE CLOSE ALL]               │
│         [RELOAD TELEGRAM]               │
│         [RELOAD BYBIT]                  │
└──────────────────┬──────────────────────┘
                   │ POST /api/control/...
                   ▼
            settings.db:
            - parser_enabled: bool
            - trading_enabled: bool
            - force_close_requested: bool
            - reload_telegram_requested: bool
            - reload_bybit_requested: bool
                   │
                   │ (бот читает каждые N сек)
                   ▼
            ┌─────────────────────┐
            │ TradingBot main loop│
            │                     │
            │ if not parser_enabled:  skip parsing
            │ if not trading_enabled: skip ордер
            │ if force_close_requested: market close + reset
            │ if reload_telegram_requested: reconnect + reset
            └─────────────────────┘

Задачи

  1. Добавить в settings.db ключи: parser_enabled, trading_enabled, force_close_requested, reload_telegram_requested, reload_bybit_requested
  2. В main.py главный loop добавить периодическую проверку этих флагов (например, раз в 2 сек)
  3. Поведение по флагам:
    • parser_enabled=false — игнорировать новые Telegram-сообщения (или Telethon handler возвращается без обработки)
    • trading_enabled=false — парсер пишет сигнал в БД, но BybitExchange.place_order не вызывается
    • force_close_requested=true — закрыть все открытые позиции market-ордерами, сбросить флаг в false
    • reload_telegram_requested=true — disconnect + reconnect Telethon, сброс флага
    • reload_bybit_requested=true — пересоздать BybitExchange instance, сброс флага
  4. Endpoints POST /api/control/<action> — пишут в settings.db и возвращают новое состояние
  5. На dashboard — кнопки с подтверждением для опасных действий (force_close_all требует ввод «CONFIRM» в модалку)
  6. Логировать каждое управляющее действие в logs/control.log с timestamp и причиной (если есть текстовое поле)

Acceptance criteria Phase 4

  • Pause parsing — новые сигналы из Telegram не попадают в БД (или попадают со status=skipped)
  • Stop trading — парсятся, в БД пишутся, ордер не уходит
  • Force close — все открытые позиции закрываются за 30 сек
  • Reload Telegram — connection в статусной карточке мигает offline → connected
  • Все действия логируются с timestamp
  • Бот ни разу не упал из-за управляющих команд (graceful обработка)

Phase 5 — Hard restart через polkit (опционально, 0.5 дня)

Цель: кнопка «Hard restart» на dashboard, которая через polkit дёргает systemctl restart tg-parser без sudo-пароля. Нужна на случай deadlock'а, когда soft control не помогает.

Опционально. Soft control из Phase 4 покрывает 95% случаев. Hard restart нужен только если бот завис намертво. Можно отложить и реализовать позже, если возникнет реальная необходимость.

Задачи

  1. Создать polkit rule для разрешения botuser рестартить tg-parser.service без пароля
  2. Endpoint POST /api/control/hard_restart вызывает subprocess.run(["systemctl", "restart", "tg-parser"])
  3. Кнопка на dashboard с двойным подтверждением (модалка с вводом «RESTART»)

Polkit rule

// /etc/polkit-1/rules.d/50-tg-parser.rules
polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.systemd1.manage-units" &&
        action.lookup("unit") == "tg-parser.service" &&
        (action.lookup("verb") == "restart" || action.lookup("verb") == "stop") &&
        subject.user == "botuser") {
        return polkit.Result.YES;
    }
});

Acceptance criteria Phase 5

  • botuser может рестартить tg-parser.service без пароля через systemctl
  • Кнопка в UI рестартит сервис, dashboard через 15–20 сек снова active
  • Подтверждение «RESTART» обязательно — случайно не нажать

5. Хранение секретов

Рекомендуемый паттерн — .env файл с правами 600 и подгрузкой через systemd:

# /opt/tg_parser/.env (chmod 600, владелец botuser)
TELEGRAM_API_ID=1234567
TELEGRAM_API_HASH=abc...
TELEGRAM_BOT_TOKEN=123:abc...
BYBIT_API_KEY_TESTNET=...
BYBIT_API_SECRET_TESTNET=...
BYBIT_API_KEY_MAIN=...
BYBIT_API_SECRET_MAIN=...
ACTIVE_ENV=testnet     # или main

WEB_HOST=0.0.0.0
WEB_PORT=8001
WEB_USER=admin
WEB_PASSWORD_HASH=$2b$12$...    # bcrypt, если basic auth включаем

LOG_LEVEL=INFO

Установка прав:

sudo chown botuser:botuser /opt/tg_parser/.env
sudo chmod 600 /opt/tg_parser/.env
# Проверка — только botuser может читать:
ls -l /opt/tg_parser/.env
# -rw------- 1 botuser botuser 512 ... .env

В systemd unit: EnvironmentFile=/opt/tg_parser/.env — переменные подгружаются и доступны процессу через os.getenv().

В коде config.py читать через python-dotenv для локальной разработки (вне systemd) или просто os.getenv() — systemd сам выставит переменные.

6. Деплой и обновления

Первичная установка

# На сервере, под root:
useradd -r -s /usr/sbin/nologin botuser
mkdir -p /opt/tg_parser
chown botuser:botuser /opt/tg_parser

# Клонируем код (или rsync с локалки)
sudo -u botuser git clone https://github.com/<you>/tg_parser.git /opt/tg_parser
cd /opt/tg_parser

# venv
sudo -u botuser python3 -m venv venv
sudo -u botuser ./venv/bin/pip install -r requirements.txt

# Секреты
sudo cp .env.example /opt/tg_parser/.env
sudo nano /opt/tg_parser/.env       # вписать реальные значения
sudo chown botuser:botuser /opt/tg_parser/.env
sudo chmod 600 /opt/tg_parser/.env

# БД (если переносим с Windows)
sudo cp /path/to/copied/db/*.db /opt/tg_parser/db/
sudo chown -R botuser:botuser /opt/tg_parser/db /opt/tg_parser/logs

# systemd
sudo cp deploy/tg-parser.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now tg-parser
sudo systemctl status tg-parser

Обновление кода

# После пуша в GitHub:
cd /opt/tg_parser
sudo -u botuser git pull
sudo -u botuser ./venv/bin/pip install -r requirements.txt   # если изменились deps
sudo systemctl restart tg-parser
sudo systemctl status tg-parser
sudo journalctl -u tg-parser -n 50

При обновлении БД-схемы — добавить миграцию в код (через _upgrade_db функцию по образцу vwma_bot), чтобы рестарт сам мигрировал.

7. Финальный чеклист — миграция считается завершённой когда…

  • ☐ Бот стартует автоматически при загрузке сервера (Phase 2)
  • ☐ Бот рестартует при ручном kill -9 через ≤ 15 секунд (Phase 2)
  • ☐ Web UI открывается с любого устройства LAN по http://<server-ip>:8001 (Phase 1)
  • ☐ На главной dashboard видны: bot status, Telegram status, Bybit status, # сигналов сегодня, # активных сделок (Phase 3)
  • ☐ Кнопка Pause работает — парсер перестаёт обрабатывать новые сигналы (Phase 4)
  • ☐ Кнопка Stop Trading работает — сигналы парсятся, ордера не отправляются (Phase 4)
  • ☐ Кнопка Force Close требует ввод подтверждения, закрывает все позиции (Phase 4)
  • ☐ Логи доступны через journalctl -u tg-parser и в файлах logs/ (Phase 2)
  • ☐ Все управляющие действия логируются в отдельный logs/control.log (Phase 4)
  • ☐ Секреты в .env с правами 600, владелец botuser (раздел 5)
  • ☐ Никаких упоминаний PyQt6, pywin32, .bat, .ico в коде (Phase 1)
  • ☐ Все тесты (если есть) проходят на Linux окружении
  • ☐ Reboot сервера — после загрузки бот сам активен через 30–60 сек
  • ☐ (Опц.) Hard restart кнопка работает через polkit (Phase 5)

После всех галочек — testnet прогон 1 неделю, потом переключение на mainnet ключи в .env + рестарт.
