Работа с оркестратором

Памятка по orchestrator + worker pattern'у для разработки и миграции tg_parser. Тот же подход, что используется в vwma_bot — позволяет вести проект через несколько Claude Code-сессий без потери контекста и без перерасхода токенов.

1. Зачем оркестратор

1.1. Проблема длинных чатов

Миграция tg_parser — это 5 фаз работы (см. migration_to_linux.html). Если вести её в одном чате, упрёшься в три проблемы:

  • Context-лимит. Окно Claude Code ~200K токенов. После compaction теряются детали ранних решений.
  • Стоимость. Каждый turn в большом чате обрабатывает весь предыдущий контекст. К концу миграции turn в 5–10× дороже стартового.
  • Скорость. Длинные чаты медленнее.

1.2. Решение — два типа чатов

Orchestrator-чат
долгий, недели

Планирует, читает прогресс, выдаёт промпты, ведёт docs/progress.html. Не пишет код. Минимум контекста на turn.

Worker-чат
короткий, одна задача

Получает self-contained промпт от оркестратора, делает работу (код+тесты+коммит), сообщает результат назад. Закрывается после коммита.

1.3. Передача контекста между чатами

Контекст НЕ передаётся через память — он передаётся через файлы:

  • CLAUDE.md — core-знания о проекте (автозагружается в любую сессию)
  • docs/migration_to_linux.html — план миграции, roadmap
  • docs/progress.html — текущее состояние (ведётся оркестратором)
  • git log + commit messages — история действий

Любая новая сессия Claude Code (orchestrator или worker) восстанавливает контекст из этих источников.

2. Архитектура pattern'а

┌────────────────────────────────────────────────────────────────┐
│  Orchestrator chat (одна сессия может жить недели)             │
│                                                                │
│  Что хранит в голове:                                          │
│    - Roadmap (5 фаз миграции из migration_to_linux.html)       │

│    /orchestrator block  → зафиксировать блокер                 │

                       │ промпт               │ "/orchestrator done abc123"
                       ▼                      │

│  Worker chat (одна задача = одна сессия)                       │
│                                                                │

│  5. git commit с осмысленным сообщением                        │

└────────────────────────────────────────────────────────────────┘

3. Команды оркестратора

КомандаКогда вызыватьЧто делает
/orchestrator В начале каждой orchestrator-сессии Startup-ритуал: читает progress.html, запускает git log/git status, сверяет с roadmap, отчитывается status report'ом
/orchestrator next Когда готов запустить новый worker-чат Готовит copy-pasteable промпт со всем контекстом (задача, ссылки на доки, acceptance criteria). Промпт самодостаточный — worker не должен возвращаться за разъяснениями
/orchestrator done <hash> Когда worker-чат закоммитил результат Читает git show <hash>, проверяет соответствие задаче, обновляет progress.html (done → ✅), планирует следующую задачу
/orchestrator block <desc> Когда worker сообщил о блокере, или нашёл blocker сам Фиксирует в progress.html → Blockers. Если требует решения пользователя — задаёт вопрос через AskUserQuestion
/orchestrator pause В конце orchestrator-сессии Обновляет progress.html, закоммитит его (docs(progress): ...), даёт summary что сделано / что дальше / какие блокеры
/orchestrator costs Раз в 1–2 недели, или когда хочется проверить бюджет Запускает skill session-report:session-report с окном 7 дней. Генерирует ./session-report-YYYYMMDD-HHMM.html

Команды worker-чата

tg_parser изначально не имеет project-specific slash commands и subagents (как у vwma_bot). После миграции можно их добавить по аналогии. На время миграции worker использует:

  • ruff check <files> — линтер
  • ruff format <files> — форматтер
  • pytest tests/ — тесты (если есть)
  • git commit — коммит
  • Subagent pr-review-toolkit:code-reviewer — code review перед коммитом сложных изменений
  • Subagent pr-review-toolkit:silent-failure-hunter — проверка на silent failures (особенно важно для управляющих endpoint'ов)

Файлы session-report-*.html добавить в .gitignore — они генерируются локально и не коммитятся.

6. Setup оркестратора для tg_parser (один раз)

tg_parser ещё не имеет настроенного оркестратора (на момент написания). Перед стартом миграции нужно подготовить инфраструктуру:

6.1. Создать CLAUDE.md в корне проекта

Файл-память, который автозагружается во все Claude Code сессии в этом проекте. Минимальное содержимое:

  • Краткое описание: что делает tg_parser
  • Стек: Python 3.11+, FastAPI, Telethon, pybit, aiosqlite
  • Точки входа: main.py (бот), web_server.py (FastAPI)
  • Текущая фаза: migration to Linux (ссылка на docs/migration_to_linux.html)
  • Sensitive areas: торгует реальными деньгами на Bybit, изменения в логике торговли — с осторожностью
  • Где секреты: .env файл (gitignored)
  • Code style: ruff format, line-length 120, type hints где разумно

6.2. Скопировать .claude/commands/orchestrator.md из vwma_bot

Файл C:\MyPyProjects\vwma_bot\.claude\commands\orchestrator.md — это slash-command оркестратора. Скопируй его в C:\MyPyProjects\tg_parser\.claude\commands\orchestrator.md с правками:

  • Заменить ссылки на Doc/ → docs/ (у tg_parser маленькая буква)
  • Заменить ссылки на strategy.html, architecture.html, rules.html → migration_to_linux.html + другие docs, если появятся
  • Заменить упоминания фаз 0–14 → 5 фаз миграции
  • Убрать sacred-rules про strategy_core.py (у tg_parser нет такого инварианта)
  • Убрать упоминания project-specific агентов vwma_bot (strategy-invariant-guardian и др.) — у tg_parser их пока нет

6.3. .claude/settings.json (опционально)

Project-level settings с allowlist для типовых dev-команд: ruff, pytest, git status/diff/log, python -c. Можно скопировать структуру из vwma_bot и адаптировать.

6.4. Привязка к GitHub repo

Если планируешь хранить миграционную копию tg_parser отдельно от оригинала — создай новый GitHub repo (например tg_parser-linux) и привяжи к копии проекта (по образцу vwma_bot).

6.5. Запуск первого /orchestrator

После шагов 6.1–6.3 открой новый Claude Code чат в копии проекта, набери /orchestrator. Оркестратор:

  1. Прочитает CLAUDE.md и docs/migration_to_linux.html
  2. Запустит git log — увидит свежий repo
  3. Создаст docs/progress.html по шаблону (с пятью фазами миграции в статусе ⬜ pending)
  4. Отдаст status report и предложит первую задачу

8. Когда оставаться в одном чате

  • Маленький фикс (5–10 минут): поправил опечатку, добавил docstring
  • Тесно связанные работы: добавление endpoint + сразу тест в одном чате
  • Архитектурное обсуждение: пока выясняем дизайн — один чат до момента «теперь знаем что делать»
  • Багфикс с воспроизведением: написал тест воспроизводящий баг → чинишь — один чат

9. Когда обязательно новый чат

  • Новая Phase: Phase 1 → Phase 2 — всегда новый orchestrator-цикл
  • Context уже compaction'нулся: чувствуешь, что Claude забывает ранние детали
  • Долгая пауза (день+)
  • Смена контекста: было удаление Windows-файлов, теперь web UI — разные части, новый чат
  • Параллельные задачи: один чат фиксит баг, другой пишет следующую фазу
  • После принятия решения: было exploration, теперь implementation

10. Troubleshooting

Оркестратор начал писать код

Скажи: «остановись, ты оркестратор, не делай работу сам — выдай промпт через /orchestrator next». Если повторяется — открой новый orchestrator-чат, ролевое поведение «забылось».

Worker не вернулся с hash

В orchestrator-чате: /orchestrator done без аргумента — оркестратор посмотрит git log, найдёт последние коммиты, спросит какой считать выполненной задачей.

Worker сделал не то что просили

git revert <hash> в worker-чате (или новом). Зафиксируй причину в orchestrator: /orchestrator block worker неправильно понял задачу X, нужен переформулированный промпт. Оркестратор переформулирует на следующем next.

Progress.html рассинхронизировался с git

В orchestrator-чате: «прочитай git log --oneline -30, сверь с progress.html, перестрой Done под реальное состояние».

Слишком много turn'ов в orchestrator-чате — стало дорого

/orchestrator pause → закрой чат → открой новый и снова /orchestrator. Свежий контекст. progress.html держит всю историю.

Worker торгует реальными деньгами на mainnet — страшно

Это не баг pattern'а, это правильное ощущение. Для миграции tg_parser обязательно используй testnet ключи Bybit на сервере до завершения Phase 5 + одного спокойного дня testnet-прогона. Mainnet включается только после полного чеклиста (см. migration_to_linux.html → раздел 7) + личного подтверждения.
